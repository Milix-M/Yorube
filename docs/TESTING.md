# CIテスト

CIと同じ検証はJDK 17で実行します。

```sh
./gradlew :app:jacocoTestReport :app:jacocoCoverageVerification :app:assembleDebug --build-cache --no-daemon
python3 scripts/test_summary.py app/build/test-results/testDebugUnitTest
```

行カバレッジの条件は100%です。JaCoCoのHTML・XMLレポートとJUnitの結果はCIの `test-reports`、APKは `app-debug` に保存します。ジョブのSummaryには件数・失敗数・スキップ数と遅いテストを表示します。テスト時間の合計にはコンパイルや環境準備の時間を含みません。

## テストを追加・変更するとき

- 操作の結果を確認します。オブジェクトの存在だけや、初期値のままでも満たせる条件を成功判定にしません。
- イベントの非到達を確認するときは、別の対象にはイベントが到達したことも確認します。
- 例外を起こすテストでは、例外を投げる処理を実際に呼んだことを確認します。通知無効などの早期returnで成功するのを防ぎます。
- 実行中の接続を保持するだけならMockWebServerの `NO_RESPONSE` を使い、クライアントを終了させてからサーバーを終了させます。固定の長いレスポンス遅延と終了リトライは使いません。
- HTTP要求は `takeRequestOrFail()` など期限付きで待ちます。必要な要求が来ない場合はテストを失敗させます。
- 中断や競合そのものを調べる短い遅延は残しています。単に待機時間を削って、目的の状態が起きなくなる変更は避けます。

## 2026-11-07の改善

他会話へのイベント漏出、複数会話の監視、監視中のサービス再開始、通知送信の失敗、新しいIntentによるActivityの再生成を確認するテストを強化しました。長いレスポンス待ちをなくし、40か所のHTTP要求待ちに期限を付けました。

本体コードに一時的に「Activityを再生成しない」「他の会話の監視をキャンセルする」という不具合を入れ、対応する2テストがそれぞれ失敗することも確認しました。検証後、本体コードを復元しています。

同じWindows・JDK 17環境で、JUnit XMLのテスト時間を比較しました。1回ずつの計測であり、CI全体の所要時間やキャッシュの効果とは分けて扱います。426件すべて成功、スキップ0件、カバレッジ3173/3173行は維持しています。

| 計測対象 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 全テスト時間の合計 | 242.31秒 | 86.29秒 |
| 複数会話の監視 | 30.12秒 | 0.14秒 |
| 監視中のサービス再開始 | 30.04秒 | 0.09秒 |
| 別会話への再接続を無視する判定 | 10.03秒 | 0.08秒 |

Gradleのキャッシュは[公式setup-gradle](https://github.com/gradle/actions/blob/main/docs/setup-gradle.md)を使用します。PR内の後続コミットでキャッシュを再利用できる設定です。JaCoCoとAGPによる同じ単体テストのHTMLレポートの重複生成をやめ、テスト・カバレッジ検証・APKを1回のGradle起動で処理します。
